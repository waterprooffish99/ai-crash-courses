## 🧠 Big Picture

There are two different directions when you work with AI:

| Direction | Best format | Simple reason |
| --- | --- | --- |
| You → AI | **Markdown** | It gives clear structure, so the AI has less to guess. |
| AI → Human | **HTML** | It can be designed, visual, easy to scan, and easy to share in a browser. |
| AI → AI | **Markdown** | It is compact and easier for models to process than decorative HTML. |

### Important technical terms

Markdown  
Plain text with simple marks such as `#` headings and `-` bullets. It matters because the structure tells the AI what belongs where.

HTML  
The language browsers render as web pages. It matters because it can present long information with layout, tables, diagrams, and controls.

Specification (spec)  
A precise document describing what the AI should build, what rules it must follow, and what is outside the task.

Asymmetry  
The two directions are intentionally different: Markdown going in, HTML coming out.

## Part 1: The Two Languages

### 1\. Why agents need structure

**What it is:** Structured instructions separate the goal, requirements, limits, and exclusions.

**Why it matters:** An AI can sound confident even when it guessed wrong. Good structure reduces guessing.

**Simple example:** Instead of saying, “Make me a nice shop page with prices and contact,” write separate sections for Goal, Requirements, Hard constraints, and Out of scope.

**Exam point:** Anything the AI must not get wrong should have its own heading or bullet, not be hidden inside a long sentence.

### 2\. The asymmetry: Markdown in, HTML out

**What it means:** The best format for giving instructions is not always the best format for reading the answer.

**Why HTML for humans?** It can show tables, visual hierarchy, diagrams, tabs, collapsible sections, and interactive controls.

**Why Markdown for AI?** HTML contains lots of layout tags. Those tags can add unnecessary text when the next reader is another model.

**Exam question to remember:** *Who reads this last?* Human in a browser → HTML. AI later → Markdown. Social feed → usually plain text.

## Part 2: Markdown, the Writing Language

### 3\. Headings

Heading = a title that tells the AI the role and importance of a section.

```text
# Main title
## Major section
### Subsection
```

Use one `#` main title. Keep levels in order. A specific heading is stronger than a vague one.

**Better:** `## Budget: PKR 50,000 hard ceiling`  
**Weaker:** `## Budget`

### 4\. Lists: bullets vs numbers

**Bullets** mean a set of independent items. **Numbered lists** mean a sequence where order matters.

```text
- Mobile-first
- WhatsApp button
- Price table

1. Review the draft
2. Correct mistakes
3. Publish it
```

Checkable bullet = a requirement that can be marked clearly as done or not done.

“Make it fast” is vague. “Loads in under 3 seconds on a slow connection” is checkable.

### 5\. Code fences

Code fence = triple backticks around text the AI should treat mainly as data or an example.

````text
```text
ERROR: Connection timed out
```
````

This helps separate quoted material from your instructions. It is a strong signal, not a security guarantee.

**Exam point:** Use fences for error messages, quoted text, code, and examples of the output format you want.

### 6\. Links and images

Markdown link:

```text
[Course page](https://example.com)
```

Markdown image:

```text
![Description of the image](image.png)
```

Alt text = the words inside the image brackets. It explains the image to tools or people who cannot directly see it.

### 7\. Your first complete specification

A reusable spec skeleton:

```text
# [Thing] Specification

## Goal
What you are making and who it is for.

## Context
Facts, links, files, and background the AI needs.

## Requirements
- Checkable requirement
- Checkable requirement

## Hard constraints
- Rules that must not be broken

## Out of scope
- Things you do NOT want

## Expected output
Describe or show the required result.
```

**Why “Out of scope” matters:** it prevents unnecessary extra features.

**Why “Expected output” matters:** it reduces format drift.

**Best habit:** Ask the AI to find ambiguities, missing constraints, and grade the spec before building from it.

**Exam point:** In spec-driven work, the specification is not just paperwork. Improving the spec improves every regenerated output.

## Part 3: HTML, the Reading Language

### 8\. Why ask for HTML?

Use HTML when an answer is long, visual, shared, or something you will revisit.

-   **Information density:** tables and diagrams can replace walls of bullets.
-   **Navigability:** table of contents, tabs, collapsible sections.
-   **Shareability:** opens in a browser.
-   **Interactivity:** buttons, sliders, toggles, draggable cards.
-   **Copy-back loop:** a tool can export your choices as text for the AI.

**Caveat:** HTML usually costs more tokens than plain Markdown and can become heavy if it uses large images or libraries. Do not use it for every tiny answer.

### 9\. You do not write HTML, you brief the AI

The course does **not** expect you to hand-code HTML for this workflow. Your skill is writing a good brief and judging the result.

Four things to include:

1.  **Who** will read it.
2.  **What** it must contain.
3.  Whether it should be **interactive**.
4.  **How** it will be read, such as once on a phone or repeatedly as a reference.

**Exam point:** “Make an HTML page” is not enough. Reader + contents + interaction + reading situation makes a strong brief.

### 10\. Five common HTML patterns

| Pattern | Simple use |
| --- | --- |
| Plans & explorations | Compare several choices side by side before deciding. |
| Explainers & reports | Turn long information into a visual summary. |
| Code review | Show changes, annotations, and flow diagrams. |
| Design prototypes | Use controls to choose colors, spacing, sizes, and other visual preferences. |
| Throwaway editors | Make a temporary tool for sorting, ranking, or prioritizing items. |

### 11\. When the destination is a social feed

LinkedIn, Facebook, and WhatsApp are not normal web pages. Their post bodies do not render arbitrary HTML.

| Destination | Best output |
| --- | --- |
| WhatsApp message | Short plain text, with only the platform's simple formatting. |
| LinkedIn / Facebook post | Plain text written for the platform. |
| Web page shared in the post | HTML. |
| Designed social graphic | Create the design, then export/share it as an image. |

Open Graph tags = hidden page metadata social platforms can use to build a link preview card.

### 12\. Publishing: from HTML to a link

The course gives several possible publishing paths. The important concept is that **building a page** and **publishing it on the internet** are separate steps.

-   Built-in AI artifact publishing: fastest for a quick public link.
-   GitHub Gist: useful for keeping one file.
-   GitHub Pages: good for a lasting site if you use Git.
-   Netlify: simple deployment of a static HTML file.

**Privacy warning:** a public link should not contain private information.

### 13\. When the destination is a document

The final format should match what the recipient will do with it.

| What the person needs to do | Format |
| --- | --- |
| Just read it in a browser | HTML |
| Sign, print, or archive it | PDF |
| Edit or comment | DOCX |
| Present it | PPTX |
| Work with numbers/formulas | XLSX |
| Feed clean structured data to a tool or AI | CSV |

**Exam point:** The deciding question becomes: *Who reads this last, and what will they do with it?*

## Part 4: One Job, Three Motions

Motion = one way of working with an AI agent.

### 14\. The three motions

| Motion | What it means | Best when |
| --- | --- | --- |
| Chat | You paste context into a conversation. | Your information fits comfortably in chat and you want quick iteration. |
| Terminal | An AI coding tool works with files and folders on your computer. | Your context is spread across many local files. |
| Desktop | A visual app works with local files, usually with approval steps. | You want file access without living in a command line. |

The **skill stays the same**: clear structured input, correct output format, review, and iteration.

## 🎯 What You Must Remember

1.  **Markdown is mainly for precision and machine-readable structure.**
2.  **HTML is mainly for rich human reading in a browser.**
3.  Always ask: **Who reads this last?**
4.  For a good spec, remember: **Goal, Context, Requirements, Hard constraints, Out of scope, Expected output.**
5.  Bullets are sets. Numbers are sequences.
6.  Use fenced blocks when showing literal data, code, errors, or examples.
7.  Do not ask only for “HTML.” Brief the reader, content, interaction, and reading situation.
8.  Use the recipient's real working format when HTML is not appropriate: PDF, DOCX, PPTX, XLSX, or CSV.

## 🛠️ Practical Work

The official crash course is hands-on. These exercises are the most important ones to actually practice:

1.  **Messy notes → structured Markdown:** Take one messy paragraph and divide it into Goal, Hard constraints, Already handled, and Open questions.
2.  **Bullets vs numbered list:** Give the same five items to an AI once as bullets and once as numbered steps. Ask how it interprets each.
3.  **Practice code fences:** Put an error message inside triple backticks and ask the AI to analyze it.
4.  **Write a real spec:** Use the six-part spec skeleton. Ask the AI to grade it for clarity, completeness, and checkability. Improve it until it is strong.
5.  **Markdown → HTML:** Take one long answer and ask for a mobile-friendly single HTML page with headings, a small table of contents, a table, and one diagram.
6.  **Build a tiny HTML tool:** Make a Now / Next / Later prioritizer with draggable cards and a “Copy as text” result.
7.  **Complete pipeline:** Use your improved spec to generate an HTML page, review it on your phone, improve it, then publish it using an appropriate method.
