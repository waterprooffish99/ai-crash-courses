# Architecture Proposal

Proposal date: 2026-10-07

## Recommendation

Build a static site with **Eleventy and a shared course shell**, while keeping each course's educational body as carefully migrated semantic HTML.

This is a shared-template static site, not a client-side single-page application. Eleventy should generate plain HTML into `website/dist/`; visitors should receive readable pages even when JavaScript is disabled. JavaScript should enhance only specific features such as quizzes, glossary filtering, flashcards, reading progress, and prompt copying.

This recommendation corresponds most closely to **C: convert the pages into a shared template/component system**, implemented with a lightweight static-site generator. It deliberately avoids a heavier application framework.

Eleventy fits because it supports reusable layouts, structured data, custom permalinks, and static output without requiring runtime JavaScript. Its official documentation describes layout/content composition, configurable output directories, and deployment to ordinary static hosts: [Eleventy layouts](https://www.11ty.dev/docs/layouts/), [configuration](https://www.11ty.dev/docs/config/), and [deployment](https://www.11ty.dev/docs/deployment/).

## Alternatives considered

| Approach | Strengths for this project | Weaknesses for this project | Decision |
|---|---|---|---|
| Publish the 10 files mostly as-is | Fastest; maximum visual fidelity; no build tooling | No homepage or shared navigation; duplicated inline CSS/JS; inconsistent accessibility and metadata; hard to add courses safely | Reject as final architecture; useful only as visual/content reference |
| Plain hand-maintained static HTML/CSS/JS | Minimal dependencies; fast pages; deploys everywhere | Shared headers, metadata, Previous/Next links, and course lists must be duplicated or generated by a custom script; drift returns quickly | Viable for a tiny one-off site, but weaker maintenance model than a small SSG |
| Retain individual pages with a shared shell | Preserves distinctive course bodies; lower migration risk; common header/footer/nav | Requires a reliable build/include mechanism; arbitrary page CSS can leak into the shell; still needs data and validation conventions | Adopt this content strategy inside Eleventy |
| Lightweight static-site generator (Eleventy) | Shared layouts/data, clean static output, no client runtime requirement, host-portable, easy future courses | Adds a Node build dependency and template syntax; migration needs careful escaping/content checks | **Recommended** |
| Modern component framework/SSG (Astro, Next.js, etc.) | Strong component model and future integrations | More dependencies and concepts than 10 mostly static lessons need; easier to introduce hydration/client complexity; migration does not benefit enough | Do not use initially; reconsider only if the site later needs substantial authenticated or data-driven behavior |
| Client-side SPA | Rich app interactions | Poor fit for static educational pages; unnecessary JavaScript, routing, accessibility, and SEO complexity | Reject |

## Why this fits the inspected source set

- The source pages are already semantic educational documents, not application screens.
- There are no image pipelines, external data calls, or server features requiring a full web framework.
- Most interactions are small and local.
- A course manifest can drive homepage cards, sitemap entries, breadcrumbs, Previous/Next links, canonical URLs, and YouTube URL placeholders from one source of truth.
- Shared CSS removes repeated resets/tokens/layouts while course-level accent variables preserve individual identity.
- Shared enhancement modules can replace duplicated quiz code and improve accessibility once.
- Static output keeps deployment simple, fast, inexpensive, and portable.

## Course data model

`website/src/_data/courses.json` should be the only source of course ordering and stable public identifiers. Each item should contain:

```text
id
order
title
shortTitle
slug
summary
sourceHtml
sourceVideo
sourceHtmlSha256
sourceVideoSha256
officialSourceUrl (nullable)
youtubeVideoId (nullable)
accentTheme
status
```

Nullable values must remain null rather than being guessed. The build should fail on duplicate IDs/slugs, missing course files, non-contiguous order, or invalid adjacent-course references.

Each course page should have:

- global site header and course-list link
- page-local table of contents
- preserved educational content
- optional YouTube embed placeholder, replaced only after a video is published and approved
- source attribution block
- Previous Course / All Courses / Next Course controls
- canonical URL, meta description, Open Graph/Twitter metadata, and structured breadcrumb/course data where justified
- one H1 and consistent landmarks

## Visual and interaction system

Use one dark, mobile-first base theme with shared spacing, type, surface, border, and focus tokens. Give each course one accent palette rather than cloning its entire source stylesheet.

Preserve useful distinctions:

- course 9's stage colors
- course 10's case/data/capability/people status model
- course-specific memory boxes, warning boxes, exam callouts, and examples
- side navigation for long pages where it improves scanning
- native `details` disclosures
- course 2's glossary and flashcards
- prompt-copy interactions

All enhancements should follow progressive enhancement:

- quiz questions and answers are rendered in HTML; JavaScript scores them
- buttons remain actual `button` elements
- flashcards use buttons or disclosure elements and work by keyboard
- status/result regions use `aria-live`
- tables retain semantic headers and gain captions where context is not otherwise clear
- a skip link and strong `:focus-visible` style are global

## Deployment comparison

### Cloudflare Pages

**Best fit and primary recommendation.** It can build from GitHub/GitLab, produces branch/PR preview URLs, supports custom domains, and serves static assets without per-request charges on both free and paid plans. The current free plan documents 500 builds per month, 20,000 files per site, and a 25 MiB per-file limit: [Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/), [preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/), [limits](https://developers.cloudflare.com/pages/platform/limits/), [pricing](https://developers.cloudflare.com/pages/functions/pricing/), and [custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/).

Fit for this project:

- Eleventy output is plain static files.
- Preview deployments support review before production.
- A later custom domain is straightforward.
- The 25 MiB asset limit is not a blocker because original videos must not be shipped in the website artifact; the public site should embed YouTube after approved publication.
- SEO is fully supported because complete HTML is generated at build time.

### Vercel

Excellent developer experience, Git-triggered builds, generated preview URLs, automatic HTTPS, custom domains, and static output configuration. It also recognizes Eleventy. Current documentation states that Hobby is free but limited to non-commercial personal use, which may matter for a public educational brand or organization: [account plans](https://vercel.com/docs/plans), [Hobby plan](https://vercel.com/docs/plans/hobby), [builds](https://vercel.com/docs/builds), and [custom domains](https://vercel.com/docs/domains/working-with-domains/add-a-domain).

Fit for this project:

- Technically excellent and probably the simplest alternative.
- Use as the primary platform only if the human confirms Hobby eligibility or approves a paid plan.
- Do not upload source videos as static site assets.

### GitHub Pages

The simplest GitHub-native static host. A custom GitHub Actions workflow can build Eleventy and publish the artifact. Custom domains and HTTPS are supported. GitHub Pages is available on public repositories with GitHub Free; private-repository availability depends on the GitHub plan: [publishing source and Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) and [custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages).

Fit for this project:

- Good zero-extra-provider option.
- Project-site base paths require more care unless a custom domain or user/organization site is used.
- Native preview deployment workflow is less convenient than Cloudflare Pages or Vercel.
- Repository visibility and content-rights decisions must be settled first.

## Deployment recommendation

Use **Cloudflare Pages** as the primary target, with:

```text
Project root: website/
Build command: npm run build
Output directory: dist
Production branch: main
```

Keep the build host-agnostic. `website/dist/` should deploy unchanged to Cloudflare Pages, Vercel, GitHub Pages, or any ordinary static host. Do not add provider-only runtime functions unless a real requirement appears.

No deployment should happen until the human approves the platform/account, public repository strategy, domain choice, and content rights.

## Migration strategy

1. **Freeze and verify sources.** Keep the SHA-256 manifest and fail validation if any original changes.
2. **Approve canonical data.** Confirm titles, slugs, source URLs, language policy, and attribution wording.
3. **Create the shell first.** Build tokens, base layout, homepage, course layout, site navigation, metadata component, and course manifest with placeholder content.
4. **Pilot one complex page.** Migrate course 2 first because it exercises glossary, copy, quiz, flashcards, long content, and attribution. Compare extracted text, heading inventory, tables, links, exercises, and question counts against the source.
5. **Build shared interactions.** Replace page-specific JavaScript with progressive, accessible modules and data attributes. Preserve no-JavaScript readability.
6. **Migrate remaining pages in order.** Keep course-specific accents/components only where educationally useful. Never edit source HTML.
7. **Add SEO and course sequence.** Generate descriptions, canonical URLs, Open Graph data, sitemap, breadcrumbs, and Previous/All/Next from the manifest; all factual descriptions must reflect source content.
8. **Validate locally.** Build, crawl internal links/assets, run HTML/accessibility checks, test keyboard use and responsive widths, and compare content inventories.
9. **Prepare deployment configuration.** Do not connect accounts or publish until approved.
10. **Add YouTube embeds later.** Only after human-approved uploads exist; use privacy-enhanced embeds where appropriate and avoid loading them until requested.

## Risks and mitigation

| Risk | Mitigation |
|---|---|
| Educational content is dropped during extraction | Automated source-vs-generated text/headings/table/question inventory plus human side-by-side review |
| Source files accidentally change | Read-only policy, stored SHA-256 hashes, and pre/post validation |
| Shared CSS erases useful course identity | Shared tokens/layout plus limited course accent themes and purpose-specific components |
| Quiz behavior regresses | One tested data-driven quiz module; HTML-first questions; no-JS fallback |
| Accessibility issues persist | Semantic landmarks, skip link, focus-visible, fieldset/legend, aria-live, keyboard tests, automated and manual audits |
| Missing official attribution is guessed | Nullable source URL; implementation blocked for attribution completion or explicit human approval |
| Product-specific facts age | Display source attribution and review date; mark time-sensitive sections; do not silently change originals |
| Clean URLs differ by host | Generate directory `index.html` routes and test using the chosen production base URL |
| Videos accidentally enter website builds | Keep `sources/videos/` outside build input; preserve Git ignores; assert no MP4/MOV/MKV/WEBM in `dist/` |
| Hosting plan mismatch | Confirm commercial/personal status and repository visibility before account connection |
| Static-host file limits | Do not host course videos in the website artifact; embed approved YouTube videos later |
| Framework dependency churn | Pin lockfile, use minimal plugins, emit portable static files, document build command |

## Implementation phases

### Phase 0 — Human decisions

- approve canonical titles and slugs
- supply/approve missing official source URLs
- confirm English-only vs future Urdu/localized website scope
- confirm content/video publication rights
- approve Cloudflare Pages or choose an alternative
- decide repository visibility and future domain ownership

### Phase 1 — Foundation

- scaffold Eleventy under `website/`
- add course manifest, shared layout, design tokens, homepage, and URL generation
- add automated build/content/link/accessibility checks

### Phase 2 — Pilot migration

- migrate course 2
- implement accessible shared quiz/glossary/copy/flashcard modules
- prove content-integrity comparison and responsive behavior

### Phase 3 — Full course migration

- migrate courses 1 and 3–10 in canonical order
- preserve important per-course features
- add site-level navigation and attribution blocks

### Phase 4 — SEO and validation

- add descriptions, canonical/Open Graph metadata, sitemap, robots, and structured data
- test pages, links, assets, keyboard operation, mobile widths, and no-JavaScript behavior
- verify original checksums again

### Phase 5 — Deployment readiness

- add host configuration and deployment documentation
- produce a local production build
- wait for human approval before connecting accounts or publishing

### Phase 6 — YouTube package (later phase)

- create the reusable per-course metadata records and support files
- derive chapters only when reliable
- prepare approval checklists
- do not upload or publish without explicit human approval

## Human decisions required before implementation
